Interfaces are state machines. Write them that way.

Declare each view's states, what it renders, and the effects it accepts. FOAR catches impossible transitions and missing cases at compile time, then updates the DOM in place without a virtual DOM.

Note.foar
view Note { store text: String = "Explicit states, not flags.";
state Viewing { render { Text(text) Button("Edit") -> on_click(Edit) } effect Edit() { transition Editing; } }
state Editing { render { Input(value: text) -> on_input(Type) Button("Save") -> on_click(Save) } effect Type(t: String) { text = t; } effect Save() { save_note(text) -> transition(Saving); } }
state Saving { render { Spinner("Saving…") } on_exit { transition Viewing; } }
}

Four booleans, sixteen combinations, three that make sense.

Flags describe states indirectly, and every combination nobody designed is a bug waiting for the right sequence of clicks. In FOAR, each state owns its view and its handlers.

Note.jsx Implicit boolean flags 
const [editing, setEditing] = useState(false);
const [saving, setSaving] = useState(false);
const [error, setError] = useState(null);

async function save() {
  if (saving) return;      // guard the impossible
  setSaving(true);
  try { await saveNote(text); setEditing(false); }
  catch (e) { setError(e); }
  finally { setSaving(false); }
}

return saving ? <Spinner />
  : editing ? <Editor … />
  : <Viewer … />;

The actual state is reconstructed from flags on every render, and every handler has to guard against combinations it cannot handle.

Note.foar Explicit states 
state Viewing {
    render { Viewer(text: text) -> on_edit(Edit) }
    effect Edit() { transition Editing; }
}

state Editing {
    render { Editor(text: text) -> on_save(Save) }
    effect Save() {
        save_note(text) -> transition(Saving);
    }
}

state Saving {
    render { Spinner("Saving…") }
    on_exit { transition Viewing; }
}

A view is always in exactly one state. Saving while saving is not guarded with an if: the Saving state has no Save handler.

Exhaustive match, checked before anything runs.

match has no fall-through and no break. It must cover every variant of an enum, both true and false, or a _ arm, and arms that can never run are compile errors. Add a variant and every match that forgets it stops compiling, naming what is missing.

Patterns support literals, a | b, inclusive ranges like 1..=9, and bindings with if guards. Use match as a value, a statement, or as Match(…) in render so the DOM swaps only when the active arm changes. Enum values compile to plain strings, costing nothing in JSON or at runtime.

checkout.foar 
enum Payment { Card, Transfer, Invoice }

let fee = match method {
    Payment.Card => 0.29,
    Payment.Transfer => 0,
};

Match(cart.len()) {
    0 => Text("Your cart is empty"),
    1..=9 => CartList(items: cart),
    n => Text("{n} items, showing the first 9"),
}

One small language for the whole interface.

State transitions, exhaustive branching, fine-grained DOM updates, styling, and translations live in the same compiler.

Explicit state machines

Views declare states, effects belong to states, and transitions are a single statement. Async work is a state with an on_exit hook.

Checked at compile time

Exhaustive match on enums. Unknown views, states, effects, styles, variants, and imports report file, line, column, and suggestions.

Retained DOM, no virtual DOM

Elements compile to blocks with direct bindings. Updates patch only changed values, keyed lists reuse rows, and inputs keep focus and selection.

State-aware styling

Scoped CSS with design tokens, dark mode, nested @hover and @media rules, and @state Editing { … } blocks that track the machine.

Built-in i18n and accessibility

t(key, params) with pluralization, RTL support, and a catalog checker. First-class label:, role:, and aria: props on every element.

Rust compiler and browser IDE

One Rust codebase builds both the native CLI and WebAssembly. The browser playground includes completions, hover docs, rename, diagnostics, and formatting.

Measured numbers, honest limits.

Every figure below comes directly from running pnpm bench and building the 21-file Notes app in this repository.

13 KB Gzipped runtime as a single ES module with zero dependencies.
32 ms Compile time for a 21-file, 2,000-line app natively or in WebAssembly.
0 DOM elements created per keystroke when filtering a 500-row keyed list.
~2 ms Per keystroke or checkbox toggle across 500 rows in happy-dom.

happy-dom is a pure-JS DOM without layout or paint and is much slower than a browser engine, so treat millisecond timings as relative; DOM elements created is the invariant work metric.

How FOAR compares

FOAR brings Elm's exhaustive matching, Svelte's compiled updates, and XState's statecharts directly into the syntax.

Dimension React Svelte Elm FOAR
Component state Flags in hooks Mutable variables Single model + messages Explicit states per view
Exhaustive branching Opt-in via TypeScript No Yes Yes: enums, bools, guards
Derived values useMemo + dependency list $derived Functions of the model let, no dependency list
DOM updates Virtual DOM diff Compiled, fine-grained Virtual DOM diff Compiled bindings, retained DOM
Styling External or CSS-in-JS Scoped <style> External or elm-css In the language, state-aware
Compiler JS (Babel / TS) JS Haskell Rust: native and WebAssembly

FOAR is early: there is no router, no server-side rendering, and no package ecosystem yet, and effect code compiles to JavaScript without a full type checker. Read the full list of trade-offs.

Start in the browser or run locally.

The Rust compiler runs directly in your browser via WebAssembly, or natively from the command line.

  1. No install: open the playground and compile FOAR right in this tab.

  2. Run locally: requires Rust and Node.

    git clone https://github.com/josmanvis/FOAR && cd FOAR
pnpm install && pnpm dev

  3. Compile a standalone bundle:

    foar build app.foar --format js -o dist/app.js

    Mount with mount(element, { bindings }). See the guide for host bindings and theming.
