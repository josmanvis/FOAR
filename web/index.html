A UI language · Rust → WebAssembly

Interfaces are state machines. Write them that way.

Declare each view's states, what it renders, and how it responds. FOAR catches impossible transitions and missing cases, then compiles to a small runtime that updates the DOM in place.

Note.foar
view Note {
    store text: String = "";

    state Viewing {
        render {
            Text(text)
            Button("Edit") -> on_click(Edit)
        }
        effect Edit() { transition Editing; }
    }

    state Editing {
        render {
            Input(value: text) -> on_input(Type)
            Button("Save") -> on_click(Save)
        }
        effect Type(t: String) { text = t; }
        effect Save() { save_note(text) -> transition(Saving); }
    }

    state Saving {
        render { Spinner("Saving…") }
        on_exit { transition Viewing; }
    }
}
States, not flags

One state at a time, and the code says which.

A view is always in exactly one state. Each state lists what it renders and the events it handles, so save while saving isn't a bug you guard against: it has no handler. Loading is a state you enter and leave, not a flag you set in one place and forget to clear in another.

The playground draws this from the source and shows each component's live state.

The problem

Four booleans, sixteen combinations, three that make sense.

Flags describe states indirectly, and every combination nobody designed is a bug waiting for the right order of clicks.

Note.jsx
const [editing, setEditing] = useState(false);
const [saving, setSaving] = useState(false);
const [error, setError] = useState(null);

async function save() {
  if (saving) return;      // guard the impossible
  setSaving(true);
  try { await saveNote(text); setEditing(false); }
  catch (e) { setError(e); }
  finally { setSaving(false); }
}

return saving ? <Spinner />
  : editing ? <Editor … />
  : <Viewer … />;

The real state is reconstructed from flags on every render, and every handler guards against combinations it can't handle.

Note.foar
state Editing {
    render { Editor(text: text) -> on_save(Save) }
    effect Save() {
        save_note(text) -> transition(Saving);
    }
}

state Saving {
    render { Spinner("Saving…") }
    on_exit { transition Viewing; }
}

state Viewing {
    render { Viewer(text: text) -> on_edit(Edit) }
    effect Edit() { transition Editing; }
}

Each state is written once. Impossible combinations can't be expressed, so there's nothing to guard.

Enums & exhaustive match

A better switch: the compiler checks every case.

match has no fall-through and no break. It must handle every variant of an enum, or true and false, or have a _ arm, and arms that can never run are errors. Add a variant and every match that forgets it stops compiling, with a message saying which.

Patterns cover literals, a | b, ranges like 1..=9, and name if guard. A match is a value, a statement, or, as Match(…), a piece of UI that swaps only when the arm changes. Enum values compile to plain strings, so the safety costs nothing at runtime or in your JSON.

checkout.foar
enum Payment { Card, Transfer, Invoice }

let fee = match method {
    Payment.Card => 0.29,
    Payment.Transfer => 0,
};

Match(cart.len()) {
    0 => Text("Your cart is empty"),
    1..=9 => CartList(items: cart),
    n => Text("{n} items · showing the first 9"),
}

What's in the box

One small language for the whole interface.

⇄

Explicit state machines

Views declare states, effects belong to states, transitions are one statement. Async work is a state with an on_exit.

✓

Checked at compile time

Exhaustive match on enums. Unknown views, states, effects, styles, variants and imports are reported with file, line and a "did you mean".

⚡

No virtual DOM

Elements compile to blocks with bindings. Updates write only changed values, keyed lists reuse rows, and inputs keep focus and selection.

🎨

Styling built in

Scoped CSS with themes, dark mode, nested @hover/@media, and @state Editing { … }: styles that follow the state machine.

🌍

i18n & accessibility

t(key, params) with plurals and right-to-left, plus a catalog checker. label:, role:, aria: everywhere, and keyboard-operable by default.

🦀

Rust compiler, browser IDE

One Rust compiler builds a native CLI and WebAssembly. The playground has completions, hover docs, live errors, rename, references and a formatter.

By the numbers

Small, and fast by construction.

13 KBgzipped runtime, one ES module, zero dependencies
32 msto compile a 21-file, 2,000-line app, natively or as WebAssembly in the browser
0elements created per keystroke when filtering a 500-row list that keeps the same rows
≈2 msper keystroke or checkbox toggle with 500 rows, measured in happy-dom

Measured with pnpm bench and the Notes app in this repository. happy-dom is a JavaScript DOM without layout or paint, much slower than a browser's, so treat its times as relative; "elements created" is the real work metric.

Get started

Try it in the browser, or run it locally.

  1. No install: open the playground. The Rust compiler runs there as WebAssembly.
  2. Locally: you need Rust and Node. 
    git clone https://github.com/josmanvis/FOAR && cd FOAR
pnpm install && pnpm dev        # http://localhost:3000
  3. Build an app: 
    foar build app.foar --format js -o dist/app.js
    Then mount(element, { bindings }). See the guide.
